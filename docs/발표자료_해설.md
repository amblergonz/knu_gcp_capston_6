## 1. HTML 설계 문서 — 섹션별 해설

7개 섹션. 위에서 아래로 **데이터 → 규칙 → 화면 → 사람** 순서로 좁혀진다.

### 1.1 처리 파이프라인

브라우저 DOM 이벤트 하나가 개입 팝업이 되기까지의 변환 단계.

- **박스** = 그 단계에서 데이터가 어떤 모양인지
- **화살표 옆 작은 상자** = 그 변환을 수행하는 실제 모듈 이름
- **시안색 선** = 본류가 아닌 주입 경로 (설정, Gemini)

읽는 순서는 위에서 아래. 오른쪽 위에서 설정 데이터가 들어와 워커에 합류하는 구조다.

> **발표 포인트** — 설정이 파이프라인 *바깥*에서 주입된다는 점.
> 운영자가 값을 바꾸면 워커가 다음 루프에서 다시 읽으므로 재배포·재시작이 없다.

### 1.2 서비스는 서로를 호출하지 않는다

같은 파이프라인을 서비스 경계로 다시 그린 것. 파이프라인과 주장이 다르다.

- 네 서비스(ingestion 4000 · worker · decision 4001 · dashboard 4002)는 **서로를 직접 호출하지 않는다.** 전부 Redis를 통해서만 만난다.
- 개입 전달은 푸시가 아니라 **폴링**이다. 워커가 `pending:{sid}` 에 한 건을 넣고, 브라우저가 가져간다.
- decision-api는 응답을 보내기 **전에** 그 키를 지운다. 한 번만 읽히므로 응답을 놓치면 개입은 영구히 사라진다.

### 1.3 ERD — Redis 저장 구조

관계형 DB가 아니라 Redis 키 공간이다. 조인 키는 `session_id` 하나.

| 엔티티 | 타입 | TTL | 역할 |
|---|---|---|---|
| `events_stream` | Stream | 없음 (MAXLEN ~100,000) | 수집된 원본 이벤트 |
| `session:{session_id}` | Hash | 1800초 | 세션 상태 · 부스터 적립 |
| `pending:{session_id}` | String | 300초 | 대기 중인 개입 1건 |
| `cooldown:{sid}:{scenario}` | String | 86400초 | 재발화 차단 |
| `interventions_stream` | Stream | 없음 (MAXLEN ~50,000) | 감사 로그 |
| `hover:config:*` | String ×3 | 없음 | 운영자 조정값 · 워커 발행본 · undo |

**ClickHouse와 PostgreSQL은 이 그림에 없다.** 설계만 있고 어느 코드도 쓰지 않아 프로젝트에서 제거했다(§2.3 참고).

### 1.4 스키마

세 개의 계약이 시스템을 묶는다.

- **이벤트 수집** `POST :4000/events` — 열거형 밖의 타입이 하나라도 섞이면 **배치 전체가 400**으로 거절된다
- **개입 전달** `GET :4001/decision/{session_id}` — 200 또는 204, 원샷
- **설정 문서** `hover:config:effective` — 워커가 기준값과 조정값을 병합해 매 루프 발행

16개 이벤트 타입의 역할 구분도 여기 있다. **부스터 소스 10 · 장바구니 2 · 수집만 4**.

### 1.5 부스터와 임계치

intent 점수는 **활성 부스터 가중치의 단순 합**이다. 머신러닝 확률값이 아니다.

설계 원칙: **단일 신호로는 어떤 시나리오도 발화하지 않는다.**

### 1.6 유저 플로우

- 예약 퍼널 6단계에서 화면별로 어떤 신호가 나오는지
- 개입이 뜬 뒤 쿠폰이 결제까지 닿는 경로
- 운영자가 값을 바꿔 반영되기까지 4단계

**시연 순서 주의사항**이 여기 있다. S1이 우선순위가 높지만 실제로는 시간상 먼저 조건이 충족되는 쪽이 나간다.

### 1.7 페르소나

예약자 3 + 운영자 2. 각 카드가 **행동 → 신호 → 점수 → 결과** 체인을 그대로 따라간다.

> **발표 포인트** — 세 번째 예약자 **이도현**이 핵심이다.
> 신호를 다섯 개나 켰는데 0.40으로 **아무것도 뜨지 않는다.**
> 그냥 둘러보는 사람을 붙잡지 않는 것이 붙잡는 것만큼 중요하다는 근거다.
> 다섯 번째 **한소영**은 `scored_boosters` 와 `config_version` 필드가 왜 존재하는지를 설명한다.

## 2. 포스터 PPTX — 무엇을 왜 고쳤는가

### 2.1 고친 이유

포스터의 A/B 수치가 **노트북이 실제로 산출한 값과 전부 달랐고, 결론이 정반대였다.**

근거 파일: `notebooks/outputs/ab_results.json` (노트북이 저장한 산출물)

```json
{
  "t_rate": 0.7864,      "c_rate": 0.7217,
  "chi2": 2.3794,        "p_value": 0.122948,
  "uplift": 8.95,        "significant": false
}
```

| 항목 | 실제 산출값 | 수정 전 포스터 |
|---|---|---|
| Treatment 전환율 | 0.786% | 12.4% |
| Control 전환율 | 0.722% | 7.1% |
| χ² | 2.379 | 4.68 |
| p-value | **0.1229** | 0.031 |
| 유의성 | **`false`** | "α=0.05에서 통계적으로 유의" |

노트북 마크다운에도 `비유의 (합성 데이터 한계)` 라고 적혀 있다.

또한 노트북 스스로 이렇게 명시한다 — **"합성 A/B (랜덤 분할)이므로 실제 개입 효과 측정 불가"**.
`np.random.random() < 0.5` 로 그룹을 나눴을 뿐 개입을 실제로 준 게 아니라, 두 그룹의 차이는 원리상 노이즈다.
**어떤 숫자를 쓰든 "개입 효과"로 제시할 수 없다.**

### 2.2 데이터셋 수치도 틀렸다

| 수정 전 포스터 | 실제 (실행된 `03_feature_engineering.ipynb`) |
|---|---|
| Retailrocket **270만 이벤트** | **274,415행 / 176,661 세션** — 약 10배 과장 |
| OTTO 1,200만 세션 · 5분↑ **Lift 1.4×** | Retailrocket **lift 32.19×** (5분↑ 체류), **8.76×** (재조회) |

노트북 실행 상태:

| 노트북 | 코드셀 | 실행됨 |
|---|---|---|
| `01_retailrocket_eda` | 13 | **0** |
| `02_otto_eda` | 4 | **0** |
| `03_feature_engineering` | 8 | **8** |
| `04_ab_synthetic` | 7 | **0** (단 `outputs/ab_results.json` 은 존재) |

OTTO 노트북은 본문에 `분석 시 100만 샘플 사용 **예정**`, `동일 방향성 확인 **예정**` 이라고 적혀 있다. 즉 분석이 수행되지 않았다.

### 2.3 수정 내용

**A/B 블록 → 설계 검증 블록** (레이아웃 구조는 그대로 재사용)

```
수정 전                              수정 후
────────────────────────────────    ────────────────────────────────
A/B 테스트                           설계 검증
합성 트래픽 1,000 세션                단일 신호로는 발화하지 않도록
treatment vs control 50:50           가중치·임계치 배치

control  개입 없음      7.1%         최대 단일 신호        0.30
treatment  개입        12.4%         최저 임계치 S2        0.42

+5.3%p                               0.30 < 0.42
χ²(1)=4.68 · p=0.031                 12종 단독 발동 시 두 임계치
→ α=0.05에서 통계적으로 유의          모두 미달 — 실측 확인
```

**체크리스트 4항목**

| 수정 전 | 수정 후 |
|---|---|
| 임계치 도출 · Retailrocket 270만 이벤트 | **가중치 근거** · Retailrocket 17.7만 세션 — 5분↑ 체류 lift 32.19× · 재조회 8.76× |
| 부스터 근거 · OTTO 1,200만 · Lift 1.4× | **오탐 차단** · 앰비언트 신호 전체 합 0.40 < 0.42 |
| 과발화 차단 (오탐 차단과 중복) | **판정 일관성** · 워커·프론트 점수 소수점까지 일치 · 부스터 12종 회귀 검사 자동화 |
| E2E 검증 | **E2E 검증** · S1·S2 실발화 · 콘솔 조정 5초 내 반영 |

**산출물 칩** — `시뮬레이터 1,000명` → `E2E 자동 검증`

시뮬레이터는 존재하지만 기본값이 10명이고, 더 중요하게는 **S1·S2를 구조적으로 발화시킬 수 없다.**
`packages/simulator/src/simulator.js` 의 `Math.random() * (EVENT_TYPES.length - 1)` 이
배열 마지막 원소인 `add_to_cart` 를 절대 뽑지 않기 때문이다. 부하 생성기일 뿐이다.

**한계 문구**

> 수정 후 — 전환 효과는 미측정. 합성 A/B 는 랜덤 분할이라 개입 효과 분리 불가. 실사용 A/B 필요.

노트북이 스스로 적은 한계와 일치한다.

### 2.4 아직 확인이 필요한 것

- **`70%↑ 복수 OTA 동시 비교 후 이탈`** — 레포 어디에도 근거가 없다. 외부 리포트라면 출처를 한 줄 넣고, 아니면 빼는 게 안전하다.
- **글자 크기** — 본문 최소 5.8pt, 비교 블록 7.3pt. A0 출력이면 괜찮지만 **A4나 화면 PDF면 읽히지 않는다.**
- **실제 렌더 확인** — 이 환경에 LibreOffice·pdftoppm 이 없어 이미지로 보지 못했다. 도형 좌표와 텍스트 밀도로만 검증했다. PowerPoint 로 한 번 열어볼 것.

## 4. 예상 질문과 답변

### 데이터·통계

**Q. A/B 테스트 결과가 어떻게 되나요?**
> 아직 없습니다. 합성 데이터로 돌려봤지만 랜덤 분할이라 개입 효과를 분리할 수 없어서, 그 수치는 포스터에서 뺐습니다.
> 대신 **오탐을 구조적으로 막도록 설계했고 그걸 검증했습니다.** 최대 단일 가중치 0.30이 최저 임계치 0.42보다 낮아서 어떤 신호 하나로도 개입이 나가지 않고, 일반 탐색 신호를 전부 합쳐도 0.40이라 발화하지 않습니다. 12종 각각 단독으로 쏴서 실측 확인했습니다.

**Q. 가중치는 어떻게 정했나요?**
> Retailrocket 176,661 세션을 분석해 5분 이상 체류가 구매 lift 32.19배, 재조회가 8.76배라는 걸 확인했고, 그게 체류·이탈 계열 부스터의 근거입니다.
> 다만 복사·멀티탭 같은 신호는 그 데이터셋에 없어서 상대적 순위로 배치했습니다. 실사용 데이터로 재조정할 부분입니다.

**Q. FP Rate 0.0%라고 하지 않았나요?**
> 그건 **구 룰 기준**입니다. 당시엔 부스터 2종에 `cart≥1 AND intent≥0.6` 이었고, 지금은 12종에 `cart≥2 AND intent≥0.52` 입니다. 다른 시스템의 수치라 인용하지 않습니다.

**Q. 그럼 효과를 어떻게 증명하나요?**
> 지금 증명한 건 **"필요 없는 사람에게 쿠폰을 주지 않는다"** 까지입니다. 전환 개선은 실사용 A/B 로만 증명할 수 있고, 그게 다음 단계입니다. 지금 없는 걸 있다고 하지 않는 게 낫다고 판단했습니다.

### 기술

**Q. 마우스 좌표를 정말 안 쓰나요?**
> 코드 전체에 `mousemove` · `clientX` · `clientY` 수집이 0건입니다. 유휴 판정의 리셋 소스에서도 마우스 이동을 뺐습니다. 멘토 요구사항이었고, 이게 이 프로젝트의 정체성입니다.

**Q. 개인정보는 어떻게 되나요?**
> 로그인이 필요 없는 익명 세션이고 30분 뒤 만료됩니다. 이탈한 뒤에는 추적하지 않습니다.
> 결제 폼에서도 **입력값은 전송하지 않습니다** — 체류 시간, 수정 여부, 길이만 보냅니다.

**Q. 1.5초 안에 개입한다는 게 가능한가요?**
> 목표치입니다. 탭 숨김처럼 판정에 직결되는 이벤트는 디바운스를 건너뛰고 즉시 전송하고, 브라우저는 300ms 간격으로 폴링합니다. 워커는 스트림을 블로킹 읽기로 대기하다 이벤트가 오면 바로 처리합니다.
> 다만 **설정 변경 반영은 별개로 최대 5초** 걸립니다. 워커가 루프마다 설정을 다시 읽기 때문입니다.

**Q. 16개 신호라고 했는데 전부 판정에 쓰이나요?**
> 아니요. **수집은 16종, 판정에 관여하는 건 12종**입니다. `page_view` · `click` · `scroll` · `page_lifecycle` 4종은 수집만 합니다. 이탈 의도와 무관해서 일부러 부스터로 올리지 않았습니다.

**Q. ClickHouse는 왜 없나요?**
> 설계는 했지만 구현하지 않아서 컨테이너째 제거했습니다. 저장소는 Redis 하나입니다. 코드가 쓰지 않는 인프라를 다이어그램에 남겨두면 있는 것처럼 보이니까요.

**Q. 워커를 여러 개 띄우면 어떻게 되나요?**
> **개입이 중복 발화합니다.** consumer group 없이 `XREAD` 하기 때문에 단일 인스턴스만 실행해야 합니다. `docker-compose.yml` 주석에 명시해 뒀습니다. 수평 확장은 consumer group 도입이 선행돼야 합니다.

### 차별점

**Q. 쿠팡·테무의 쿠폰과 뭐가 다른가요?**
> 네 가지입니다.
> **감지 대상** — 저희는 경쟁사로 새는 순간을 직접 잡습니다. 탭 전환, 객실명 복사, 외부 예약사이트 클릭. 쿠팡·테무는 자사 내부 행동만 봐서 다른 사이트를 보는지 모릅니다.
> **개입 시점** — 세션 안에서 되돌립니다. 이탈 후 푸시·리타게팅은 이미 타사에서 결제가 끝났을 수 있습니다.
> **발화 기준** — 독립 신호 2개 이상 + 쿨다운 24시간 + 세션당 2회 상한. 전원 살포가 아닙니다.
> **할인 설계** — 의도 점수에 비례해 5/10/15% 차등. 잃을 위험이 큰 손님에게만 크게 씁니다.

**Q. 왜 호텔 예약인가요?**
> 복수 사이트 동시 비교가 표준이고 객단가가 높아서, 한 건을 되돌렸을 때 효과가 가장 큰 도메인입니다.

### 운영

**Q. 쿠폰이 너무 자주 나가면 어떻게 하나요?**
> 운영 콘솔에서 신호를 끄거나 가중치를 내리면 됩니다. **배포도 재시작도 없이 5초 안에 반영됩니다.** 그게 이 시스템이 스스로를 증명하는 지점입니다.
> 화면에서 "활성 가중치 합이 임계치보다 낮아 발화 불가" 같은 경고도 그 자리에서 띄웁니다.

**Q. 신호를 끄면 데이터도 사라지나요?**
> 아니요. **수집은 계속되고 점수에서만 빠집니다.** 껐다 다시 켜면 그동안의 기록까지 소급해서 점수에 들어옵니다.

**Q. 왜 이 손님에게 이 할인이 나갔는지 설명할 수 있나요?**
> 개입 페이로드에 `scored_boosters`(실제 채점된 신호)와 `config_version`(그때 설정 버전)이 들어 있습니다. 어떤 신호가 어떤 설정으로 판정했는지 역추적됩니다.

## 5. 남은 한계 — 솔직하게

숨기지 말고 먼저 말하는 편이 방어에 유리하다.

| 한계 | 현재 상태 |
|---|---|
| **전환 효과 미측정** | 합성 A/B 는 랜덤 분할이라 효과 분리 불가. 실사용 A/B 필요 |
| **복사·멀티탭 가중치의 데이터 근거 부족** | Retailrocket 에 해당 신호가 없어 상대 순위로 배치 |
| **워커 수평 확장 불가** | consumer group 미도입, 단일 인스턴스만 |
| **전환 추적 없음** | 구매 귀속이 없어 CTR·전환율을 계산할 수 없음. 어드민에서 해당 지표를 제거함 |
| **설정 API 무인증** | 4002는 데모 전용. `CONFIG_WRITE_TOKEN` 으로 잠글 수 있으나 기본은 열림 |
| **판정 로직 이중 작성** | 워커와 프론트 미러에 같은 분기를 손으로 두 번 씀. 회귀 검사로 완화 |
| **모델 미연동** | XGBoost 부스터는 가중치 0에 모델도 없어 제거함 |

## 6. 재현 방법

주장한 숫자를 직접 확인하는 법.

```bash
# 백엔드 4종 (Docker 없이)
bash scripts/dev-backend.sh

# 데모 사이트
cd packages/demo-hotel-site && pnpm dev
# http://localhost:3000/?ref=google.com

# 어드민 대시보드
cd packages/admin-dashboard && pnpm dev   # :3001

# 부스터 12종 발동 + S1/S2 실발화 자동 검증
node packages/stream-worker/scripts/smoke-be-c.js
```

시연 순서:

- **S2** — 장바구니 비운 채 호텔 상세 진입 → 호텔명 복사(아무 일 없음) → 가격비교 표에서 외부 사이트 클릭 → 배너
- **S1** — `?ref=google.com` 진입 → 객실 2개 담기 → 스크롤 끝까지 → 결제 폼에서 멈칫 → 탭 이탈 20초 → 복귀 시 쿠폰 모달

**주의** — S1이 우선순위가 높지만 실제로는 시간상 먼저 조건이 충족되는 쪽이 나간다.
호텔명을 복사하면 그 순간 S2가 발화하므로, S1을 보여주려면 복사 없이 진행해야 한다.
같은 세션에서 두 번 보려면 SIGNAL 패널의 **새 세션 시작**을 누른다 (쿨다운 24시간).
